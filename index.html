Sample Test Case

How I write and execute a case: one precondition set, numbered steps, a specific expected result per step, and an honest status with evidence.

Login and Authentication

Admin can log in to the workflow portal

Preconditions: 1. User has an admin account. 2. User has accepted the invitation and created the account.

Step Expected result Status
1. Open the portal login page Login page shows the logo, header, Username and Password fields and the Login button Passed
2. Leave Username and Password empty Login stays disabled; helper text "Please fill in all fields to enable login" shows Blocked
3. Enter invalid credentials and click Login A generic error that does not reveal which field is wrong; user stays on the login page Blocked
4. Enter valid credentials Login becomes enabled; helper text hides Passed
5. Click Login User lands on the Dashboard (/dashboard) Passed

Blocked steps note the reason (e.g. needed a logout the session owner had not approved) so the team knows exactly what is left to run. Every passed step links to a screenshot.

API Testing

A case study: hardening a status-change endpoint that, per its ticket, accepted any status change. I designed 20 test cases to prove the new transition rules hold, including when someone tries to get around them.

ENDPOINT UNDER TEST

PATCH/applications/:id/status

Rules to prove: only allowed next statuses, only by the current assignee, approval and release only through the issuance flow, and every change written to the audit log with actor, from-status and to-status.

20 TEST CASES BY TYPE

3 happy paths 9 negative scenarios 8 edge cases

Negatives include disallowed jumps, skip-ahead and backward moves, unknown or empty values, non-assignee and unauthenticated calls. Edge cases cover same-status, CASE and whitespace tricks, spoofed body fields, concurrent and replayed requests, and cross-tenant IDs.

Requests I ran, and what came back

TC12 · Unauthenticated request is rejected

PATCH /applications/:id/status
# no Authorization header, no cookie
{ "status": "<allowed next status>" }

401Passed 

"Authentication required. Please provide a valid JWT Bearer token or API key."

Then an authenticated GET confirmed nothing changed, and the application count stayed at 42.

TC16 · Non-existent application ID

PATCH /applications/<random valid-format UUID>/status
Authorization: Bearer <token>

404Passed 

"Application with ID <uuid> not found"

TC16 · Malformed application ID

PATCH /applications/abc!@%23/status
Authorization: Bearer <token>

404PassedFinding 

"Cannot PATCH /applications/abc!@"

No 5xx, so the test passed. But the error showed the proxy had decoded %23 into # and cut the path short. I logged it as an observation for the dev team.

What every case checks, beyond the status code

  • The error message names the broken rule
  • A follow-up GET shows the state did not change
  • Audit entries are checked in the raw data with read-only SQL, not the UI
  • The audit actor matches the user ID in the JWT, even when the body spoofs it
  • No side effects ran (no license number issued)
  • Bad input never causes a 5xx server error

JUDGMENT CALL

Why most cases are Blocked

All 42 applications in the environment were real applicant records. Before the fix, the endpoint accepted any status, so one negative test could have corrupted real data or issued a real license. I ran only the safe cases and asked dev for disposable test applications for the rest.
