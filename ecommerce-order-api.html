E-Commerce Order API: Risk-Based API Test Automation

Preventing overselling and duplicate orders in an order API

I tested an e-commerce order API's highest-risk workflows (order creation, insufficient inventory, and duplicate submission) by designing positive, negative, boundary and concurrency API checks in Playwright + TypeScript, produced a reproducible test suite with an HTML report published by CI, and used the results to define release criteria for the order endpoint.

Summary · Built a personal Playwright + TypeScript API test project for an e-commerce order system, automating 46 risk-based checks (overselling, duplicate orders, cancellation), with isolated test data, CI on GitHub Actions, a published HTML report and a live demo.

Context and Problem

A simulated order-management API for a computer-peripherals store ("Deskside Supply"). Order creation is the revenue path. Two failures cause direct financial harm:

  1. A double click or client retry creating two orders and deducting stock twice.
  2. Accepting an order for more units than exist, or failing half-way and leaving stock corrupted.

I built the API and a demo storefront so these risks could be tested end to end and shown visually.

Scope

In scope

  • POST /api/orders, GET /api/orders/:id, POST /api/orders/:id/cancel, GET /api/products(/:id)
  • Request validation
  • Inventory deduction and rollback
  • Idempotency
  • Order status transitions (CONFIRMED → SHIPPED → DELIVERED, CONFIRMED → CANCELLED)
  • Error response contract
  • Demo storefront availability

Out of scope

  • Authentication / authorization
  • Payments
  • Multi-server concurrency (SQLite is single-process)
  • Idempotency key expiry (time-based)
  • Performance / load
  • Browser UI automation

Assumptions and constraints

  • Local deterministic seed data
  • Free hosting resets the database on restart
  • Tests create their own isolated data

Test Strategy

Risks scored likelihood × impact (1–25)

R-03 Duplicate submission20 Critical R-02 Insufficient inventory / overselling20 Critical R-01 Successful order creation15 Critical R-04 Input validation12 High R-05 Cancellation & status transitions12 High R-06 Error contract & traceability6 Medium

Oracles: not status code alone

Status code + headers (Content-Type, Location, X-Request-Id, Idempotency-Replayed) + strict JSON schema (zod) + business state checked afterwards (stock level, number of orders for that customer).

Data rule

Each test creates its own product with known stock plus a unique customer email and idempotency key, so tests run in parallel (4 workers) without collisions. The database is reset to a deterministic seed before every run.

Findings

Real issues found while building and verifying. No product-logic defect was found in the final order API.

  1. 1 · Onboarding blocker

    A fresh npm install tried to compile the native SQLite driver (better-sqlite3) from source. That fails on machines without C++ build tools, which includes most Windows laptops. Fix: switched to Node's built-in node:sqlite. Verified by a clean install and full test run from a fresh copy.

  2. 2 · Storefront: stale Cancel button

    Cancelled orders still showed a "Cancel order" button. Found by driving the page in a headless browser; fixed and re-checked.

  3. 3 · Storefront: misplaced request log

    The request log panel could render out of place on long pages. Fixed and re-checked with screenshots.

Quality Decision

MEETS RELEASE CRITERIA, FOR THE DOCUMENTED SCOPE

  • No overselling under concurrency
  • No duplicate orders for a repeated key
  • Atomic rollback on failure

Release-blocking checks are tagged @critical and run in CI on every push.

NOT YET EVALUATED

Authentication, payments, multi-instance concurrency, key expiry, load. Those would be required before any real production use.

Tradeoffs and Lessons

Limitation
SQLite on one process means the concurrency tests prove single-instance safety only.
Rejected option
better-sqlite3, rejected because its native build broke a clean install for new developers.
Next improvement
Inject a clock to test idempotency key expiry; then add auth with an order-ownership (IDOR) check.

Learning: a passing suite is only trustworthy once you've seen it fail for the right reason.
